# DigitalArmsLab

Освітня платформа для вивчення будови та принципу роботи зброї: 3D-моделі + анімації збірки/розбірки.

## Стек
- React 19 + TypeScript, Vite 8
- react-router-dom 7 (маршрутизація)
- yup (валідація форм)
- CSS Modules (`*.module.css`)
- 3D: @react-three/fiber + @react-three/drei (Three.js), scroll — GSAP ScrollTrigger. Один fixed-overlay Canvas, керування скролом. Постобробки НЕМАЄ свідомо (див. нижче)
- Немає: state-менеджера, data-fetching бібліотеки, тестів

## Обов'язкові принципи
- **НЕ РУХАТИ окремі частини моделей.** Будь-яка анімація геометрії — лише зашитими в glb кліпами (`idle` / `diassemble` / `assemble`). Не смикати окремі вузли, не програвати службові пер-об'єктні дії з експорту, не «досипати» рух коду. Дозволено лише ЧИТАТИ стан, який дає штатний кліп (напр. зняти габарит у кінці `diassemble`, щоб під нього розрахувати бокс).
- **SOLID** — кожна одиниця має одну відповідальність; залежності через абстракції (типи/сервіси), не через конкретику.
- **Feature-based архітектура** — код групується за фічами, не за типами файлів.

## 3D-ассети
- У прод ідуть `public/models/*.ktx2.glb` — їх робить `npm run models` зі ВИХІДНИХ `*.glb` (не з `*.opt.glb`: ті вже квантовані, повторна упаковка накладає похибку вдруге).
- Текстури — KTX2/BasisU: їдуть у GPU стисненими, без розпакування на CPU. Було 96 МБ VRAM і ~6 с блокування головного потоку на PNG/JPEG → стало ~8 МБ і секунди. Вага: дрон 7.22 → 1.15 МБ, АКМ 6.83 → 1.85 МБ.
- Стеля роздільності 1024: порівняння 2048 vs 1024 на дроні в Hero різниці не показало (він і в найбільшому кадрі ~1500px), а вага впала вшестеро.
- Потрібен НАТИВНИЙ `tools/gltfpack.exe` (npm-збірка йде без кодувальника BasisU) — тека в .gitignore, посилання в шапці `scripts/prepare-models.mjs`.
- Рантайм: моделі вантажити ЛИШЕ через `useGltfModel` (shared/Scene3D) — він підключає KTX2-транскодер із `public/basis/`. Прямий `useGLTF` не прочитає стиснені текстури.
- Моделі монтуються не разом: АКМ під'їжджає при наближенні до Features (`useApproaching`), щоб не конкурувати з дроном за перший екран.
- Перф міряти на ПРОД-збірці (`npm run build` + `vite preview`): у dev Vite віддає сотні немініфікованих модулів, і блокування головного потоку завищене в рази.

## Швидкодія завантаження
- Шрифти обрізає `npm run fonts` (`scripts/subset-fonts.mjs`, пакет `subset-font`): 1603 → 608 КБ. Вихідні файли несли повне покриття Unicode на україномовному сайті — сам NotoSansMono падав зі 145 до 20 КБ. Скрипт перезаписує woff2 НА МІСЦІ, тож повторний запуск безпечний (обрізаний файл не стає меншим), а відкат — лише через git.
- Кирилицю беремо цілим блоком U+0400–04FF, а не «лише вжиті символи»: інакше будь-який новий текст мовчки ламався б підміною шрифту.
- `font-display: swap` обов'язковий у КОЖНОМУ `@font-face` — без нього текст невидимий, доки шрифт вантажиться.
- Шрифт заголовка Hero лежить у `public/fonts/` (не в `assets/`) і має `<link rel="preload">` в index.html: ним набрано LCP-елемент, а Vite хешує імена в assets, тож послатися на них з HTML неможливо.
- Усе, що не потрібне першому екрану, чекає на `useIdle` (shared/lib): 3D-шар (`lazy` + гейт) і фонове відео (`shared/DeferredVideo`). Інакше чанк three.js на ~200 КБ і відео забирали смугу ДО того, як намалювався заголовок.
- Скрол-хореографія (`useHomeChoreography`) викликається в `HomeScene`, а НЕ в HomePage: вона тягне GSAP, і поки виклик стояв у HomePage, GSAP лежав у чанку першого екрана. Перенесення зменшило чанк HomePage зі 143 до 29 КБ. Крок картки Features хореографія віддає нагору колбеком.
- Фонове відео Hero має `opacity: 0.999` — це не косметика. Повноекранне відео Chrome виносить в апаратний оверлей, якого композитор Windows не бачить, і в мініатюрі вікна на його місці лишається зелений службовий колір. Ненульова прозорість повертає відео у звичайний композитинг.
- Заміри лише на прод-збірці з профілем PageSpeed (CPU ×4 + повільний 4G): `scratchpad/audit.mjs`. Результат роботи: LCP 7324 → 4332 мс, вага 3464 → 3141 КБ.
- Транскодер KTX2 (`public/basis/`, 515 КБ WASM) — плата за стиснені текстури. Вантажиться пізно, разом із моделлю; проти 11 МБ економії на текстурах це вигідно.

## Структура
- `src/pages/<Page>/` — сторінки рівня маршруту: `ui/` + `index.ts` (barrel).
- `src/widgets/` — композитні крос-сторінкові блоки (Header, Footer, Layout).
- `src/features/<feature>/` — самодостатні фічі:
  - `model/` — типи (`*.types.ts`), mock (`*.mock.ts`), валідація yup (`*.validation.ts`)
  - `services/` — запити (`*.service.ts`); поки бекенду нема — повертають mock
  - `hooks/` — `use-*.ts` (стан/логіка)
  - `ui/` — компоненти (кожен: папка + `*.module.css` + `index.ts`); головний збиральний файл `*Layout.tsx`
  - `index.ts` — публічний API фічі (експорт фічі + типів)
- `src/shared/` — перевикористовувані одиниці (кожна: папка + `.module.css` + `index.ts`).
- `src/features/_feature-template/` — **еталон-приклад** архітектури (контент профілю/фішингу з іншого проєкту, НЕ реальна фіча).

## Конвенції
- Компонент: `const X = () => {}` + `export default X`; пропси — inline `type XProps = {}`.
- Кожна одиниця має barrel `index.ts` (`export { default } from "./X"`).
- CSS Modules імпортуються як `css`.
- Типи — централізовано в `model/`, експортуються для перевикористання (без дублювання).
- Валідація — лише yup: `*FormValues` + `*InitialValues` + `*ValidationSchema`.
- Alias `@/` → `src/` (напр. `@/assets/svg/logo.svg`).
- UI-текст і коментарі — українською.

## Адаптивність
- Брейкпоінти (px): 1280, 1024, 900, 768, 600, 425, 375.
- **Одиниці висоти на мобільних.** Поки ховається адресна панель, видима область росте, а розкладка ще порахована за старим в'юпортом. Правило: усе, що має НАКРИВАТИ екран (fixed-шари `Scene3D`/`ScreenGrade`, `min-height` у Layout і body), задається в `lvh` — це в'юпорт у найбільшому стані, тож коротшим воно не буде ніколи. `svh` там ставити не можна: це найменший стан, і щойно панель ховається, знизу оголюється смуга. `dvh` теж не варто — він міняється щокадру переходу й тягне перерахунок розкладки (а для Hero ще й зсував би слот дрона).
- Фон задано і на `html`, і на `body`: під час переходу браузер може показати смугу поза межами body.
- Симптом «кілька смуг різного чорного знизу, лише поки палець на екрані» — це саме цей клас багів: смуга, не накрита fixed-шаром, лишається без віньєтки й зерна. Емулятор його не відтворює (там немає адресної панелі, і всі одиниці рівні) — перевіряти лише на пристрої.
- Бургер-меню: з'являється при ≤1024px. Діапазон 768–1024px — пункти меню рівняються по правому краю (бургер справа, зручніше для фокусу); <768px — рівняння по лівому (чітко як у Figma).

- **Користувач**: верстка + перенесення дизайн-системи.
- **Claude**: інтеграція анімацій, зв'язки компонентів, логіка (стани/хуки/взаємодії), 3D-розміщення та взаємодія.

## Стан та дані
- Глобальний стан — **Redux**, але лише за реальної потреби (напр. auth); де можна обійтися локальним станом — обходимось. Тека `src/redux/` (темплейт надасть користувач).
- Усе на mock; бекенду немає й найближчим часом не буде.
- У реальних задачах `services`/хуки закладають стани **loading** та **error**.

- Layout: Header (десктопна навігація + мобільне бургер-меню `MobileMenu` ≤1024px), Footer (wrapper).
- Маршрут `/` → HomePage (порожня).
- Loader (shared), еталон-фіча профілю.
- Alias `@/` → `src/` (vite.config.ts + tsconfig.app.json).
- VisionScanner (shared) — фоновий canvas-ефект «комп'ютерного зору» за курсором; приймає `className`, кладеться позаду контенту секції.
- ScreenGrade (shared) — екранний грейд сторінки (віньєтка + зерно), монтується останнім у HomePage.
- Якірна навігація: `shared/lib/anchorScroll.ts` + `useAnchorScroll` (у Layout). `NavigationLink` з `to="#id"` скасовує клік (react-router не робить нативний перехід до фрагмента), скролить `window.scrollTo({behavior:"smooth"})` з відступом на висоту хедера, URL не змінює. З іншої сторінки — якір їде через `location.state`. ID секцій: `#hero`, `#about`, `#features`, `#cta`, `#contact`.

- LaboratoryPage (`/lab`): GuideSection (+ `AudioPlayer` — риски хвилі рахуються від ширини через ResizeObserver, стан played, демо-таймлайн поки нема `src`), ArsenalSection.
- ArsenalSection: дані — фіча `features/arsenal` (model/services/hooks, mock: 4 категорії × 2 одиниці, картинки тимчасово akms). Логіка — `useArsenalSlider`: стрілки рухають вибір на 1 картку, трек зсувається на сторінку лише коли вибір вийшов за видиме вікно. Розмір вікна = `--visible-slides` (читається з CSS через `getComputedStyle`); ширина картки за замовчуванням рахується з нього так, щоб слайдер зайняв усю доступну ширину, а `--slide-width` (за замовчуванням `initial`) — необовʼязкове перекриття через `var(--slide-width, …)`. Зсув береться з `offsetLeft` картки. Безкінечність — список ×3 копії + безшовний стрибок у середню після transitionend.
- Вибір категорії: `CategoryList` (десктопна стрічка; зсув миттєвий і рівно на потрібну величину, градієнт `pointer-events:none` стоїть на тому краю, за який виїхали кнопки; `contain:inline-size` на `.strip`, щоб кнопки не роздували min-content сторінки) і `CategoryDropdown` (мобільний, розкриття через `grid-template-rows 0fr→1fr`). Обидва рендеряться завжди з однаковими пропсами, перемикання — класами `.categoryList`/`.categoryDropdown` в `ArsenalSection.module.css`.

- Фіча `arsenal` доповнена: `Weapon.modelUrl` (тимчасово akm.opt.glb для всього, крім дронів), `WeaponDetails` (опис/ТТХ/принцип роботи/джерела) у `weapon-details.mock.ts`, `getWeaponDetail(id)` + `useWeaponDetail(id)`. Активна картка слайдера — `<Link>` на `/lab/:weaponId`.
- Спільне 3D: `shared/Scene3D` експортує ще `StudioEnvironment` і `tuneMaterials` (envMapIntensity/мін. roughness).
- `StudioEnvironment` має два пресети: `study` (дефолт — рівне студійне світло, ScenePage: об'єкт треба РОЗДИВЛЯТИСЯ) і `showcase` (лендінг: майже прибраний ambient, гарячий помаранчевий контровий кант ззаду-справа, слабкий холодний заповнювач спереду — модель «виходить із темряви» і світиться тим самим помаранчем, що й сторінка). Міняти світло лендінгу — лише в `ShowcaseLighting`, `study` не чіпати, бо від нього залежить читабельність ScenePage.
- `Scene3D` (лише HomePage) — ACESFilmic + експозиція 0.95, `dpr` зі стелею 1.5. Повнокадрові ефекти сюди НЕ ставити: канвас прозорий і покриває лише 3D-шар.
- **Постобробки немає — і не додавати.** `EffectComposer` з `Bloom` подвоював кадр (16.6 → 27 мс у спокої, 53 мс під час скролу зі стрибками під 100 мс — це ~18 fps). Не лікується налаштуваннями: заміряно MSAA 0, dpr 1, півроздільну bloom — усі за межею бюджету 60 Гц, бо повноекранний mip-ланцюг коштує стільки, скільки коштує. Гарячий кант дають контрове СВІТЛО + CSS-градієнт-ореол у секції; bloom додавав до цього мало.
- `shared/ScreenGrade` — віньєтка + плівкове зерно `position:fixed` поверх усього (z-index 1001, `pointer-events:none`). Свідомо поза канвасом: грейд має лягати й на текст, і на фонове відео, інакше шари виглядають з різних джерел. Зерно ще й прибирає бандинг градієнтів на майже чорному тлі. Мерехтіння вимикається при `prefers-reduced-motion`.
- Два грабля в зерні (обидва коштували fps, обидва вже обійдені): анімувати можна ЛИШЕ `transform` (`background-position` = повноекранний repaint щокроку, і разом із шаром переcompose'иться WebGL-канвас), а сам шар має бути ледь більшим за в'юпорт (`will-change` промотує його у власний буфер, який оплачується площею; 200%×200% = вчетверо більший за екран).
- Заміри перфу робити ЛИШЕ в реальному вікні (`chromium.launch({ headless: false })`). Headless тягне софтверний SwiftShader — там усе повільне, і відносні числа теж брешуть.
- Гейтинг рендера: канвас у режимі `frameloop="demand"`, кадри запитує `FrameloopGate` усередині Scene3D, а рішення «чи потрібна сцена» дає `useSceneActivity` (IntersectionObserver на `#contact` + видимість вкладки). Перевірено: у CTA 1452 виклики малювання за 2 с, у Contacts — 0.
- Проп `frameloop` у `<Canvas>` читається ЛИШЕ при монтуванні; ні його зміна, ні `set({frameloop})` зі стора в рантаймі не діють. Єдиний робочий шлях — `demand` + власний цикл `invalidate()`.
- Вимикати рендер можна тільки там, де в кадрі вже нічого немає: зупинений цикл лишає на канвасі останній кадр, тож інакше модель застигне поверх сторінки. Межа — коли Contacts дійшов до верху в'юпорта (`rootMargin: "0px 0px -98% 0px"`; рівно −100% брати не можна — смуга нульової висоти не дає перетину).
- Що гейтинг НЕ дає: fps у Contacts майже не змінився (16.9 → 16.7 мс), бо рендер порожньої сцени й так дешевий. Виграш — нуль роботи GPU, тобто батарея й нагрів (а через нагрів — тротлінг, від якого лагає вже вся сторінка).
- `getBoundingClientRect` щокадру (5 читань) коштує 126 мкс на кадр при CPU ×4 — 0.8% бюджету. Кешувати не варто, заміряно.
- Матеріали моделей — лише через `useTunedMaterials` (shared/Scene3D): він бере максимальну анізотропію з GPU і застосовує її до всіх текстур. Без неї на дрібному рельєфі мерехтить блиск («зернистість у пазах»), особливо на телефоні.
- `minRoughness` у `tuneMaterials` був НЕробочим: у наших glb `roughnessFactor` = 1, а шорсткість лежить у текстурі. За специфікацією glTF шорсткість = множник × канал текстури, тому робочий важіль — `roughnessBoost` (>1 робить матовішим), а не мінімум.
- Мобільну зернистість НЕ відтворити локально: це артефакт реальної мобільної GPU (точність і фільтрація), в емуляції працює десктопна відеокарта. Перевіряти лише на пристрої.

Частково (перший прохід, потребує тюнінгу наживо):
- ScenePage (`/lab/:weaponId`): `WeaponViewer` — власний (не overlay) `<Canvas>` з подіями миші: `WeaponModel` (glb нормалізується bounding-сферою до `MODEL_RADIUS` і центрується, доворот з `MODEL_FACING`, тогл розбирання = кліп `diassemble`/`assemble` один раз із `clampWhenFinished`; якщо кліпу збирання нема — розбирання у зворотному напрямку) + `ViewControls` (OrbitControls без пану, зум у межах fit-дистанції; скидання виду — плавний переліт у сферичних координатах за `RESET_DURATION`, далі автообертання; ручний pointerdown його зупиняє). Тюнити: `viewer.config.ts`. Стан UI — `useSceneControls`. Решта UI: `SceneToolbar` (?, скид виду, розбирання), `WeaponCaption`, `WeaponInfoDrawer` (Esc, `inert` у закритому стані).   - Розмір моделей адаптивний за еталоном (як ScenePage): `REF` 1920×1080 + коефіцієнт `min(1, w/1920, h/1080)`; на 1920 — як задизайнено, нижче плавно меншає за меншим виміром. Дрон — `sizeFrac` від висоти еталона; АКМ — вписування у `REF_SLOT` (розміри боксів на 1920) × коефіцієнт. DOM-бокси слотів дають лише ЦЕНТР (позицію); їхній CSS-розмір не впливає на масштаб, лише має не давати горизонтального скролу (CTA `min(940px,49vw)`, Features `max-width` на ≤1024).
  - Дрон: у Hero позиція І розмір беруться з DOM-боксу `#drone-slot-hero` (порожній absolute-div у HeroSection; `left/top` = центр дрона, `width/height` = габарит) — композиція Hero тюниться в CSS, у TS лише поза. Далі десктоп (>768) — Hero→About(вправо на 30% менший, поворот вліво) + легкий ховер. Мобайл (≤768, `gsap.matchMedia`) — спуск СТРОГО по центру через About (фаза 1), тоді доворот у вид ЗГОРИ (top-down, ×1.5, сталий скейл) в окремій геп-зоні `#drone-gap` між About і Features (фаза 2, `choreo.droneGap`; висота зони — `min(72vw,380px)` у HomePage.module.css). Поріг 768 продубльовано в трьох місцях (`MOBILE_MAX_WIDTH` у DroneModel, matchMedia у useHomeChoreography, `.droneGap`) — міняти разом; в АКМ свій поріг 600 під верстку Features. Пози Hero (десктоп 3/4 носом вправо-вниз, мобайл майже фронтально) — `TUNE.heroPose`, кути в порядку Euler `ZXY`: yaw навколо власної вертикалі → pitch до/від камери → roll у площині екрана.
  - Стеження за курсором у Hero: `usePointerAim` (scene/) віддає позицію миші як мутабельний ref (−1..1 від центра, без ре-рендерів); DroneModel згладжує її кадронезалежним `damp` і додає малий доворот до базової пози (`TUNE.pointerAim`), який згасає з `1 − droneProgress` — далі в дрона своя хореографія. Pitch навмисно менший за yaw: дрон майже з ребра, тож вертикальний кут змінює силует у рази сильніше. Вимкнено на тачі та при `prefers-reduced-motion`.
  - Профіль силуету (`modelBounds` + `modelSilhouettes` у scene/math.ts) знімається ОДНИМ проходом по геометрії одразу для всіх потрібних поз. Окремі проходи (зібрати вершини → повернути → збінити, і так на кожну позу) коштували секундного фризу рівно в момент появи моделі. Читати треба лише вершини з ІНДЕКСНОГО буфера: в оптимізованих glb вершинний буфер спільний, і «сироти» роздували силует у півтора раза.
  - Вписування в бокс (`fitToBox` у scene/math.ts) враховує перспективу: плоский фіт по габаритній коробці занижував розмір на ~17% і зсував центр, бо перспективний поділ діє й на зміщення групи. Тому масштаб і позицію шукає спільна ітерація по РЕАЛЬНИХ вершинах (`collectVertices` + `rotateVertices`), результат кешується за розміром боксу — рахується на ресайзі, не щокадру. Перевірено скріншотами: бокс у CSS = силует на екрані з похибкою <1px.
  - АКМ: одна модель, трекінг DOM-бокса слота (`#akm-slot-features` / `#akm-slot-cta` — замість колишніх картинок akms); на ≤600 ×2 і у Features вертикальніший (екранний roll ~80°, `FEATURES_MOBILE_ROLL`; зникає при перельоті в CTA). Features пін на 3 кроки: картка 01/02/03 + кліпи `idle`/`diassemble`/`assemble` (скраб скролом). CTA — профіль, idle.
  - Z-контракт: медіа секцій `z-index:-2` → 3D `-1` → VisionScanner `0` → текст `≥1`; секції не мають бути stacking context.
  - Тюнити наживо: `SLOT_TUNE` (AkmModel), `DRONE_TUNE` (DroneModel).

Не готово / далі:
- 3D: тюнінг позицій/обертів; стиснення важких glb (drone 16 МБ / akm 12 МБ); перф (frameloop `always` → пауза поза екраном).
- ScenePage: реальні glb під кожну одиницю; взаємодія з окремими частинами моделі (підсвітка/клік).
- Секції HomePage — у процесі верстки.
